## 一、为什么没用 md2wechat 二开

我们评估过 [md2wechat-skill](https://github.com/geekjourneyx/md2wechat-skill)（3.8k star，很成熟），
最后决定自研。两个硬事实：

1. **那个仓库里没有排版渲染器。** `internal/converter/api.go` 里写死了
   `DefaultAPIConvertURL = "https://www.md2wechat.cn/api/convert"`，`themes/*.yaml`
   只是传给这个 API 的参数和 AI 模式的提示词。我核对了改成 BUSL 之前的 MIT 老版 v2.0.2
   （2026-03-21），结构一模一样 —— **从第一版起，Markdown→公众号 HTML 就在作者自己的服务器上**。
   所以二开它省不下排版，排版照样要买它的付费 API Key。
2. **许可是 BUSL-1.1（2026-05-07 从 MIT 升级）。** 中文条款第二节明确：

   > • 在任何**营利性组织**中将本作品用于与**商业运营直接相关**的内部工作流；
   > • 对本作品进行改名、贴牌或以不同品牌名义重新分发，**无论底层代码是否经过修改**，均须获得商业授权。

   团队内部跑商业公众号，正好落在这一条。

**结论：全自研，零授权风险、零 API 费。** 排版引擎、微信接口层、写作提示词都是我们自己的代码。

## 三、部署

```bash
# 本地（Windows 也行）
python deploy/deploy.py

# 只更新代码、不动 Caddy
python deploy/deploy.py --skip-caddy
```

脚本是幂等的，做这些事：

1. 打包 `app/ run.py requirements.txt` → 上传 → 解压到 `/opt/wxwb`
2. 建 venv（`--system-site-packages`，复用系统的 `markdown-it-py` / `Pillow` / `jinja2` / `requests`）
3. 装 `fastapi uvicorn python-multipart`
4. 写 `/etc/systemd/system/wxwb.service`，随机生成管理员密码（首次），重启服务
5. 在 `/etc/caddy/Caddyfile` 的 IP 站点里挂 `handle /wxwb*`，**先备份 + `caddy validate`，失败自动回滚**

SSH 凭据可用环境变量覆盖：`WXWB_SSH_HOST` / `WXWB_SSH_USER` / `WXWB_SSH_PASS`。

常用运维命令：

```bash
systemctl status wxwb
systemctl restart wxwb
journalctl -u wxwb -n 50
tail -f /opt/wxwb/data/logs/service.log
```

## 四、首次配置（3 步）
### 1. 公众号账号

「公众号账号」页填 AppID / AppSecret / 作者署名。

> **最容易卡住的一步**：微信要求「发起请求的服务器公网 IP」在该公众号的
> 「设置与开发 → 基本配置 → IP白名单」里，否则返回 `40164`。
> 我们这套跑在 your-server 上，这个 IP 已经在白名单里（原 `/opt/wechat-pub` 那套就在用）。
> 换服务器记得把新 IP 加进去。

填完点「体检」，返回 `token ok` + `draft_total` 就说明通了。

### 2. 模型

「设置」页填 Base URL / 模型名 / API Key。当前默认：

```
Base URL  http://127.0.0.1:7863/v1     （服务器本地直连网关）
模型      cn:deepseek-v4.1-flash
```

点「测试连通」。**Key 是加密存库的**（Fernet），界面上永远只显示"已配置"。

想换成本地模型也行，任何 OpenAI 兼容地址都可以，比如
`http://127.0.0.1:11434/v1` + `qwen2.5:14b`。

### 3. 账号人设（每个号一套）

「公众号账号」页每个号都能单独配这几项，互不干扰：

| 字段 | 作用 |
|---|---|
| **人设** | 这个号是谁、怎么说话。会拼在写作规范最前面一起喂给模型 |
| **选题领域** | 逗号分隔关键词（如 `科技,AI,手机,芯片,大模型`）。热搜页用它标注"这条适不适合本号"，模型选题时也按它筛 |
| **专属写作规范** | 留空 = 用「设置」里的全局规范；填了就整段替换 |
| **排版主题** | 这个号固定用哪个主题（科技号配冷静蓝、历史号配文艺米白） |
| **配图数量** | 0 = 跟随全局；1-8 覆盖全局 |
| （全局设置）**允许几张数据截图** | 默认 1；设 0 表示只要实拍图，不要榜单/报表截图 |
| **封面用网图做底图** | 勾上就用抓到的配图当封面底图，不勾就纯色渐变底 |

举例（直接填进「人设」框）：

```
你是「噜噜谈科技」的主笔，一个懂技术但不炫技的科技博主。语气像在行业里待过几年的人，
会算账、会拆参数，不吹不黑。喜欢用普通人能听懂的方式解释技术，经常拿身边正在用的
产品做例子。反感发布会话术和参数堆砌。
```

```
你是「旧事新说」的主笔，一个讲历史的。不从帝王将相讲，从普通人的吃穿住行、赋税、
律法讲起。每个判断都要落到具体的年代、制度和数字上，不写"自古以来"这种空话。
爱用今天的现象接古代的制度，让读者觉得历史不是过去，是另一种现在。
```

### 4. 写作规范

「设置」页的「写作规范（提示词）」是一整段可编辑的 system prompt，默认值就是你们原来那套规矩：

- 纯正文 500–800 汉字，4–6 个自然段块、1–2 个小标题、5–8 处加粗
- 语气必须主观，**禁止平衡稿**，段落按判断链走
- 标题固定「反问 + 结论」，≤15 字
- 结尾一句具体互动提问 + 8–10 个话题标签
- 全篇规避「最」字，违禁词零命中
- 财经类不预测点位、不推荐个股、不承诺收益
- 不碰政治敏感与民族宗教，不对未定性事件下结论

改完下一次生成就生效，不影响已有稿件。

## 五、日常怎么用

### 生成过程可视化

点「写这篇」/「生成」不再干等：

1. 接口**立刻返回**（实测 24ms），直接跳到稿子编辑页
2. 页面顶部出现进度条：`正在写稿… → 正在抓配图… → 收尾中`，下面是**实时滚动日志**
3. 生成期间**所有编辑控件锁定**（标题/正文/按钮全灰），手机预览显示"生成中"占位
4. 完成或失败后自动解锁、刷新预览，并把标题/摘要/正文/配图全部填好
5. 中途可以关掉页面，生成在后台继续；重新打开照样看到结果

技术实现：`POST /api/generate` 带 `async_mode: true` → 建稿子行（`status=generating`）
→ 丢进后台任务 → 前端每 1.5 秒轮询 `GET /api/article/{id}/progress`
（只查 status/stage/log 几个字段，很轻）。生成流程用 `stage` 字段汇报进度：
`queued → writing → images → done`，失败是 `failed`。

### 删除稿件

两个地方都能删：
- **首页稿件列表**每行右侧「删」按钮，删完列表原地更新，不刷新页面
- **编辑器**右下角「删除这篇稿」

删除只删工作台里的稿，**不动公众号草稿箱**（那个要用「删掉草稿箱旧稿」）。

### 首页

- 四个统计卡片可点，点「草稿中」直接筛出那批稿
- 三个快捷入口：从热搜选题 / 自己给个题（一行输入直接生成）/ 定时任务
- 稿件区：状态标签页（带条数）+ 标题搜索 + 分页（每页 8 条），列表里直接显示配图张数和更新时间
- 定时任务折叠在页面底部，不占视觉

### 从热搜挑选题（「热搜选题」页）

1. 顶上选**给哪个号写**，点「刷新热搜」：抓微博热搜实时榜（一次 40 条），按热度排序列出。
2. **分类 tab**：全部 / 文娱 / 社会 / 科技 / 财经 / 教育 / 健康 / 生活 / 体育 / ACG，每个 tab 带条数。
   账号的「选题领域」对应的那个分类会标 ★ 并自动高亮，点 tab 就只看那一类。
3. 每条会标出**领域命中**（关键词命中，或它所属分类就是这个号的主分类）和硬性排除项。
   如果这个号一条都没命中，页面会提示你换号 / 自己给题 / 仍然挑一条从本号角度切。
3. 点任意一条的「写这篇」直接开写；也可以点「让模型挑一条」，模型会按
   **热度优先 + 领域贴合 + 四条标准**给推荐，并说明理由和**轴心（切入点）**。
4. 生成完自动进编辑器。

**分类是怎么来的**：微博主榜接口（`ajax/side/hotSearch`）只给 `word / num / label_name`，
**没有分类字段**。所以分两段做：

1. **关键词规则**（`app/topics.py` 的 `CATEGORY_RULES`）—— 快、免费、结果稳定。
   顺序即优先级：ACG > 体育 > 科技 > 文娱 > 生活 > 社会（"手机发布会"归科技不归文娱）。
   英文词按单词边界匹配，避免 `ai` 命中 `waiting`。
2. **模型语义判断**（`refine_categories`）—— 真实热搜大量是"明星姓名 + 口语化短句"
   （如「两京十五日成毅拔箭这段」），关键词表天生覆盖不到，规则实测 40 条里只认出 9 条。
   所以把没认出来的批量交给模型判，一次调用搞定，结果进内存缓存（同一词条只问一次）。

想调分类边界，改 `CATEGORY_RULES` 就行；模型不可用时自动退回纯规则。
要加新分类：在 `topics.py` 里 `CATEGORIES` 加个名字、`CATEGORY_RULES` 加一组关键词、
`category_for_domain` 加一条映射、`CATEGORY_PROMPT` 里加一行定义 —— 前端 tab 会自动跟着出来。

### 自动配图（默认 4 张，可配置）

**先确认配图来源**：账号上有个 `image_source` 开关，决定这条稿子的图从哪来 ——

| 值 | 行为 | 什么时候用 |
|---|---|---|
| `web`（默认） | 走下面这套「联网抓图」 | 免费、快，但图只能尽量贴题 |
| `ai` | 走 `pipeline.generate_ai_images_for()`，逐张 AI 生成 | 要画面完全贴合内容；绑了虚拟人物就用那个人 |
| `mixed` | 先抓一半网图，剩下交给 AI | 想省钱又想有几张定制的 |

**「设置页配了 AI 生图，草稿里却全是网图」就是没切换这个开关** ——
`image_llm` 只是把生图服务接通，长文模式的配图链路原来只有联网抓图一条路
（`fetch_images_for`），压根不调用 `aigen`。这是历史遗留：AI 生图一开始只服务
「人物日常」模式和稿件页的单张「AI 重生成」，忘了给长文模式留入口。
现在两条链路统一由 `pipeline.fill_images()` 分发，生成流程和稿件页「重新配图」都走它，
不会有"按钮行为和设置不一致"的情况。

几个实现上的注意：

- AI 那条路**不自己再写一套插入逻辑**，复用 `_strip_prev_images` / `imgsource.insert_into_markdown`
  / `_cover_for`，跟网图那条完全一样。否则两份代码迟早长得不一样。
- 画面描述由 `writer.image_scenes()` 出：让模型按正文的小标题/段落给 N 个「拍什么」，
  **只写画面内容，不写镜头光线和画质**（那些由 `photo.py` 统一加，写了会打架）。
  模型失败时退化成「选题 + 小标题」，不会因为这一步把整篇稿子搞挂。
- 混合模式里网图先落地、AI 后补（`append=True`），AI 那半张失败也只是少一张，
  不会把已经抓到的网图一起弄丢。
- 单张失败只跳过那一张，一张都出不来才报错；报错时**不回退成网图** ——
  账号既然说了要 AI 图，偷偷换成网图会让人以为设置没生效。

下面是 `web` 这条路的完整流程：

1. **先让模型把选题拆成 2-3 个短关键词**再搜。这一步很关键 ——
   选题常常是长句（「内娱全女拍烂了都不如一部AI」），直接拿去搜索几乎搜不到东西，
   拆成「AI短剧、全女综艺」之后候选从 62 条涨到 204 条，出来的图也从"世界旅游景点"变成《浪姐》《中国神话》AI 微短剧
2. 拿这些关键词去 **360 图片搜索**（主图源，中文新闻图索引全）搜候选，必要时用 Bing 图片兜底；
   关键词都命中不足时，才把文章小标题也拿去兜底搜
2. 下载前就筛掉：水印图库（699pic/包图/千图…）、表情包站、视频站、竖图、比例不合适的
3. 逐张下载（15 秒超时，连续失败 15 次就止损，别在防盗链域名上硬耗）
   → PIL 校验（格式/尺寸/完整性）→ **平均哈希去重 + 同名图去重**
   （同一篇文章的配图组标题相同，6 张里出现 3 张同名很跳）
4. 按「标题与选题的词重叠」打分排序，再让**模型按标题和来源站复选**一遍
5. **先把 Markdown 规范化**：模型偶尔会输出"整篇单换行"的稿子，
   `render.normalize_markdown()` 会把它补成规范的块结构（标题/正文/列表之间加空行），
   否则段落识别、插图、排版全都会出问题
6. **排除「数据截图」**：正文里全是榜单/报表会显得很素（你们原来有这条规矩）。
   用可解释的三个信号判断 —— 边缘密度（表格线和文字行会让它飙升）、近白比例、近黑比例：
   实测照片得分 ≤0.35、榜单截图 ≥0.74，阈值取 0.55。标题带「排名/榜单/报表/统计/走势」的再加权。
   实拍图优先，数据图**排在后面**；被判成数据图的图**不会被删掉**，会进"备用区"：
   先按 `max_data_images` 配额补位，还不够就全用上 —— **宁可给数据图，也不给空位**。
   （早期版本在这里把超配额的数据图直接删了，结果一张误判就让整篇只剩 1 张图。）
7. 均匀插到正文段落之间，每张带图注；其中一张自动用作封面底图

编辑器的「配图」区能看到每张缩略图、尺寸、来源站，不满意的点「移除」
（会同时从正文删掉），或者改数量后点「重新抓图」。

### 编辑器

| 区域 | 说明 |
|---|---|
| 左 | 标题（实时显示字数、缺不缺反问句）、摘要、作者、Markdown 正文 |
| 左 | 插图：本地上传 / 从网址下载，插入时填图注（图注会渲染成 12.5px 灰字） |
| 左 | 封面预览 + 用当前标题重做（可选某张图做底图） |
| 右 | 手机预览（可切主题、可切 320/375/414 屏宽）+ 自检 + 操作日志 + 发布区 |
| 右 | 「让模型起 6 个标题」「去 AI 味」「重新写一篇」 |

**交互细节：**
- 顶部操作条**吸顶**，滚到哪都能保存/建草稿
- 左边正文滚动时，右边预览**按比例联动**滚动（反过来也会）
- 配图卡片可以**拖动排序**、**直接改图注**（失焦即存）、**换一张**（抓同选题的另一张网图）、单张移除
- 保存 / 精草稿 / 抓图 / 换图 / 改图注 都是**局部刷新**，不跳页、不丢未保存改动
- 标题字数实时算，超 15 字或没反问句会立刻提示

**自检看两栏：**

- **必须处理**（红线）：违禁词、`<h1>`、`class`、`style` 块、坏图片地址
- **建议**：字数不在区间、标题超 15 字或没反问、小标题/加粗数量不对、标签不足

### 存入草稿箱

点「存入草稿箱」，后台做的事：

1. 把 Markdown 渲染成内联样式 HTML
2. 正文图逐张走 `media/uploadimg` → 换成 `mmbiz.qpic.cn` 链接
3. 封面走 `material/add_material?type=image` → 拿 `thumb_media_id`
4. `draft/add` 建草稿
5. `draft/get` **回读校验**：图片数对不对、有没有残留本地地址、有没有 h1/style 块
6. 记录到选题库

⚠️ 正文图和封面是**两套接口**，不能混：正文图返回 `url`，封面返回 `media_id`。

### 存到头条草稿（可选）
头条号**没有对外发文接口**，所以这条链是**浏览器自动化**：Playwright 驱动真浏览器，
把稿子填进头条发文页，最后只点「存草稿」。代码里不存在点「发布」的路径。

**一次性准备（服务器上）**

`python deploy/deploy.py` 会自动搞定：装 playwright，再装浏览器内核。

- 官方 CDN（cdn.playwright.dev）在国内实测只有 **0.1–0.3 MB/s**，headless shell 126MB +
  chrome 199MB，半小时起步、经常等到超时。所以部署脚本**先测速**，慢就直接走国内镜像
  （`tools/install_browser.py`，npmmirror / 阿里云的 chrome-for-testing），实测 **12 MB/s**，
  30 秒装完；系统库走 `playwright install-deps`。
- `deploy.py --skip-playwright` 可以跳过这步（不用头条功能时）。

手动修的时候：

```bash
./venv/bin/python tools/install_browser.py --check   # 能不能启动
./venv/bin/python tools/install_browser.py --deps    # 装内核 + 系统库
./venv/bin/python tools/install_browser.py --force   # 重下（弄坏了的时候）
```

> 踩坑：`zipfile` 默认**不还原 Unix 权限位**，从镜像下 zip 解出来的
> `chrome-headless-shell` 没有 `+x`，playwright 直接报 `Permission denied`；
> 另外包里的顶层目录不能摊平，playwright 找的是
> `<安装目录>/<顶层目录>/<可执行文件>`，摊平了报 `Executable doesn't exist`。
> 这两条 `tools/install_browser.py` 都处理了。

## 六、性能与并发

**曾经很卡的根因**：所有接口都写成 `async def`，但里面用的是**同步** `requests` 调微信和模型。
单进程单事件循环，任何一次外部调用都会把整个站点冻住 —— 实测：

| 场景 | 修之前 | 修之后 |
|---|---|---|
| 打开草稿箱页 | 490ms（等微信 batchget） | **12ms**（页面只出壳，数据异步来） |
| 草稿箱数据（走缓存） | 每次 400-900ms | **2.4ms** |
| 5 个并发请求 | 串行排队 2.03s | **并行 0.5s** |
| 生成中（86 秒）访问其它页面 | 全站冻结 | **2-11ms 正常** |
| 热搜抓取 | 8-16s（等模型分类） | **0.24s**（规则分类秒出，模型分类后台补） |
| 点「写这篇」后的等待 | 20-90s 白屏干等 | **24ms 跳进编辑页**，边生成边看 |
| 编辑页打开 | — | **78ms** |

**怎么修的：**

1. 所有阻塞调用（微信接口、模型调用、图片下载）都改成 `await asyncio.to_thread(...)`，
   跑在 FastAPI 的线程池里，事件循环不再被堵
2. 草稿箱页只渲染外壳，数据由 `/api/drafts` 异步拉；服务端带 **45 秒缓存**，
   建草稿/删草稿时自动失效
3. 热搜拆成两步：`/api/topics/fetch` 只跑关键词规则（快），
   前端渲染完再调 `/api/topics/classify` 让模型补分类，tab 原地更新
4. 文章列表查询不再取 `markdown / html / log` 这几列大字段

**自己加接口时注意**：只要函数里会出现网络请求、模型调用、文件下载，
就**必须**用 `await asyncio.to_thread(...)` 包一层，否则又会把整站拖死。

**长任务一律走"后台 + 轮询"**：`asyncio.create_task(_bg_generate(...))` 起后台任务，
前端轮询 `/progress`。不要让一个请求把 HTTP 连接挂几十秒，浏览器和反代都可能超时。

## 七、微信接口踩坑清单

这些都是实测踩出来的，出问题先对一遍：

| 现象 | 原因 | 处理 |
|---|---|---|
| `40164` | 服务器 IP 不在白名单 | 公众号后台「基本配置 → IP白名单」加服务器公网 IP |
| `40125` / `40001` | AppSecret 错 / token 失效 | 重新生成 secret；程序对 40001 会自动重取一次 |
| `48001` | 该接口没授权 | 多数订阅号只能建草稿，不能 `freepublish/submit` |
| `45009` | 调太快限频 | 等几分钟；`draft/add` 已内置 3 次退避重试 |
| 排版全丢了 | content 里用了 `class` 或 `<style>` 块 | 本工作台强制内联样式，提交前会拦 |
| 标题重复出现 | content 里有 `<h1>` | 本工作台把一级标题降级成 h2 样式 |
| 图片显示不出来 | 只传了封面没传正文图（或反过来） | 正文图用 `uploadimg`，封面用 `add_material` |
| 回读中文乱码 | ①编码假象，不是数据坏了 ②`requests` 会把不带 charset 的响应用 latin-1 解码 | 校验**只认计数**（图片数、h1 数、style 块数），绝不拿中文做关键字匹配；解析统一走 `wechat._parse_json()`（强制 utf-8） |
| 选题/摘要/标签显示不对 | 参数传错（曾把图片 url 当成 keywords 传给自检） | 自检只吃 `keywords`，别把别的列表塞进去 |
| 某个页面卡住、其它页面也打不开 | 有阻塞调用没进线程池（单进程事件循环被堵） | 用 `await asyncio.to_thread(...)` 包起来，见「性能与并发」 |
| 页面里图片是破图，但草稿箱里正常 | 应用挂在 `/wxwb` 子路径下，而图片地址是 `/media/uploads/...`（没前缀），浏览器直接请求会落到站点根目录 → 404。建草稿时是按**文件名**映射本地文件再 `uploadimg`，跟 URL 无关，所以草稿箱正常 | 模板里一律用 `{{ media(m.url) }}`（`app/main.py` 里的 `media_url()` 会补前缀）；预览 iframe 里由 `app.js` 的 `previewInto()` 补前缀。**新加图片相关模板时别再手拼 `/media/...`** |
| **配图区显示 6 张，但正文里一张图都没有** | 模型输出的 Markdown 用了**单换行**（`## 小标题` 紧接正文、段间无空行），旧版插图逻辑按 `\n\n` 切块 → 只切出一块且以 `#` 开头 → 判定"没有可插位置"直接原样返回。图记进了库，却没进正文 | 已两处修掉：① `insert_into_markdown` 改成**按行找正文行**做插入点，不依赖空行；② 生成后先跑 `render.normalize_markdown()` 把单换行稿补成规范块结构；③ 插图后再兜一层校验，没插进去就规范化重插并写日志 |
| 配图全是截图/表格，太素 | 搜索引擎对"数据类"选题返回的多是榜单、报表图 | 已内置识别（边缘密度+白底/黑底比例），实拍优先、数据图最多 1 张；到「设置」里把「允许几张数据截图」设 0 就彻底不要 |
| 配图和话题不相关，出来一堆"世界旅游景点" | 长句选题直接当搜索词，搜索引掣匹配不到 | 现在先用模型把选题拆成短关键词再搜；剩余低相关的图会在配图卡片上标「相关性低」，一眼能看出该换哪张 |
| 配图和话题不相关 | 图源是搜索引擎索引，热点刚起时可能只有"沾边"图 | 改数量重抓；或在编辑器里移除换掉；说明里建议先看缩略图再建草稿 |
| 点「换一张」换回来还是同一张 | 去重比错了维度（本地文件名每次下载都会变） | 已改为按**原始图片地址 + 内容哈希**去重 |
| 图源返回 0 条 | 反爬或该词太新 | 360 → Bing 会自动兜底；仍失败就手动「从网址插图」 |
| 回读 mmbiz 计数多 1 | 有 `data-cover` 之类的字段也含 mmbiz | 断言用 `<img[^>]+src="http[^"]*mmbiz`，不要裸 count |

**事实和语气不改**。和「去 AI 味」分工明确——去 AI 味改语言，优化排版改版式。

### AI 生图（`app/aigen.py`）

可配置后端，和文本模型完全分开：

| provider | 用途 |
|---|---|
| `images` | OpenAI 兼容 `/images/generations`（智谱 CogView / OpenAI / 各种中转站）|
| `dashscope` | 阿里云百炼 · 通义万相（异步轮询）|
| `sd` | 本地 Stable Diffusion WebUI |

#### 人物参考（虚拟人物号）

做「虚拟人物号」的核心是**同一个人在不同场景保持同一张脸**：今天在工位加班、
明天在路边吃饭，脸得是同一个人。纯文字提示词做不到，所以单独有「人物」页：

```
人物页 → 建人物（名字 + 外形描述 + 画面偏好）→ 传 1~3 张参考照
      → 账号页把人物绑到某个号上 → 之后这个号的 AI 配图/封面都带这个人
```

技术上分两条路：

- **支持参考图的后端**（首选）：把参考照作为底图 + "保持长相不变，把场景改成 X" 的指令
  - `dashscope` → `POST {base}/services/aigc/image2image/image-synthesis`，模型
    `wanx2.1-imageedit`，`input.function="description_edit"`，`base_image_url` 必须是
    **公网可访问**的地址（所以「设置 → AI 生图」里有「本站对外访问地址」这一项）
  - `images` → `POST {base}/images/edits`（multipart 传图），模型如 `gpt-image-1`
  - `sd` → `/sdapi/v1/img2img`，`denoising_strength≈0.55`
- **不支持参考图的后端**（兜底）：把「外形描述」拼进提示词。长相不会被真正固定，
  界面上会明确提示"现在是按外形描述生成的"。

**参考图模型要单独填**（`ref_model`）。文生图和图生图往往不是同一个模型名；
例如中转站的 `image-2` 只能文生图，`gpt-image-2` 才能吃参考图（实测横版 1536×1024、约 45~55 秒/张）。

三个必须注意的坑：

1. **`/images/edits` 的字段名和尺寸各家不统一**：同一个中转站上 `gpt-image-2` 用 `image`，
   而 `image[]` 直接 502；有的模型只吃 `1024x1024`，传横版也 502。
   **一个错组合白等 45~50 秒**，所以代码会把试成功的 `(字段名, 尺寸)` 记到
   `settings.img_edits_combo` 里，下次直接命中——不缓存的话一张图能从 50 秒变成三四分钟。
2. **402 = 余额不足，不是参数错**。中转站会回
   `{"detail":"积分不足（当前 0，需要 10，1张）"}`。这种错误换字段名也没用，
   代码会立刻抛出可读提示，不再白试四种组合。
3. **默认加合规约束**：公众号/头条对暴露、软色情会限流甚至封号，所以参考图生成的提示词
   里写死了"日常得体服装、不要暴露、构图健康"。别去掉。

#### 镜头/动作/表情轮换（别让模型只会拍正脸）

只锁**长相**（五官、脸型、发型、肤色），机位、动作、表情每次都要换，
否则模型会一直吐同一张"正面大头照"，做人物号等于复读机。

`aigen._SHOTS` 里有 18 条 `(机位, 动作, 表情)`，每条的表情是配套挑过的
（不会出现"背着包往前走还无奈叹气"这种别扭组合）。按人物 id 在
`settings.char_shot_idx` 里记一个游标，每生成一张就轮换到下一条，
所以连续出图必然换角度。提示词里还显式写了"避免正面大头照 / 证件照构图 /
正对镜头摆拍 / 重复上一张的角度"。

`generate_scene(..., return_meta=True)` 会把本次用的机位/动作/表情一起返回，
「人物」页上直接显示，方便判断是不是又撞角度了。

实测同一人物、同一场景「在便利店买关东煮」连续两张：
一张是**全身远景走过来的环境照**，一张是**侧后方 45° 半身低头看手机**，
脸一致、构图完全不同。

#### 写实提示词工程（`app/photo.py`）

原来 `build_prompt` 是「高质量写实照片 + 画面风格 + 别摆拍」——全是形容词，一个决定画面的
具体量都没有。模型拿到这种提示词只会给一张**均匀、干净、无瑕疵**的图，那才是最典型的 AI 味。

真人拍的照片之所以一眼能认出是照片，靠的是五件能量化的事，`photo.py` 就是把这五件事写成词库：

| 维度 | 写什么 | 为什么 |
|---|---|---|
| 器材 | 具体焦距 + 光圈（26mm 手机主摄 / 35mm f/2.8 / 85mm f/2） | 透视和景深从这儿来，不是靠"浅景深"三个字 |
| 光 | 光从哪个方向来、暗部靠什么补、色温多少 | 均匀打光必出塑料感；有方向的光才有体积 |
| 质感 | 毛孔、油光、碎发、布料褶皱的阴影、玻璃上的指纹 | 写"细节丰富"没用，写能数出来的东西有用 |
| 构图 | 地平线歪一点、前景遮挡、边缘裁切、留白偏一边 | 严格居中 + 水平 = 摆拍 |
| 瞬间 | 动作进行中、快门按早半秒、焦点落在稍前处 | 摆好姿势等快门 = 摆拍 |

反过来，下面这些词**一个都不许进提示词**（`tools/show_photo_prompts.py --check` 会拦）：
`8K`、`4K`、`masterpiece`、`best quality`、`ultra detailed`、`hyperrealistic`、
`perfect lighting`、`cinematic lighting`、`award winning`、`trending on artstation`。
它们不会提升画质，只会把画面推向「渲染图」。

配套的一组负向词分四类（塑料感 / 打光 / 渲染感 / 姿势），对应 AI 味的四个来源：

- **SD**：走 `negative_prompt` 字段，整套词表都塞得下
- **OpenAI images / 万相**：只有一条 `prompt`，否定要写成自然语言「画面里不要出现：……」
  ——而且**只能挑最要命的 12 个**。实测写三四十个否定词，模型会开始丢前面的正向指令。

风格预设（设置页「生图风格」）只锁**器材 + 景深 + 光 + 调子**这四件身份性的事，
构图、瑕疵、质感、表情仍然轮换；每个风格给了两条光，按 idx 交替，
否则选完风格就变成复制粘贴。

三个坑：

1. **用 idx 自增取模，不要 random**。随机的话同一篇稿子重生成两次拿到完全不同的光，
   排查「这张为什么难看」时无法复现；而且小词库里随机经常连着撞同一个值。
   `plan()` 是纯函数，同一个 idx 一定得到同一份方案。
2. **取模的步长别和词库长度有公因数**。原来写 `idx*3` 配 6 条机位，实际只在 2 个值上打转。
   现在直接 `idx % 长度`，词库长度 6/7/5/6/4 互不整除，相邻几张必然换参数。
3. **静物和人物共用一套词库**，所以光线/色彩/瑕疵的文案里不能出现「脸」「皮肤」——
   人像专属的皮肤、头发、表情单独成字段，负向词也按 `portrait` 分流，
   否则给咖啡店配图塞一句「皮肤不那么红润」纯属噪音。

自检（改完词库跑一下，不花钱也不调接口）：

```bash
python tools/show_photo_prompts.py            # 看拼出来的提示词
python tools/show_photo_prompts.py --style film
python tools/show_photo_prompts.py --check    # CI 里跑的就是这个
```

真人生成那条路上的**合规约束没动**：参考图提示词里仍然写死「日常得体服装、不要暴露、
构图健康」。公众号/头条对这类内容会限流甚至封号，这条不是可选项。

#### 内容模式：长文 / 人物日常

账号上有 `content_mode`，两条完全不同的产线：

| 模式 | 产出 | 适合 |
|---|---|---|
| `article`（默认） | 500~800 字长文 + ## 小标题 + 5~8 处加粗 + 热搜配图 | 公众号/头条正文号 |
| `photo` | **N 张人物图 + 2~4 句口语**，标题也口语化，不带小标题和加粗 | 虚拟人物号、纯晒人的日常号 |

`photo`（人物日常）的流程在 `pipeline._run_photo_mode()`：

```
LLM 一次出：标题 + 2~4 句文案 + N 个可拍摄画面（每个画面含动作/地点，机位不重复）
  → 逐张 generate_scene（用绑定的虚拟人物，机位自动轮换）
  → 图片插在句子之间（不是全堆在末尾）→ 第一张图压字做封面
```

要点：

- **必须先绑虚拟人物**，没绑就明确报错，不会悄悄退化成普通文章
- 出图张数由账号上的 `photo_count` 控制（1~6，默认 3）
- 标题/文案走的是另一套提示词（`writer.PHOTO_PROMPT`）：**禁止**公众号那种
  「反问+结论」标题、禁止小标题、禁止结尾升华
- **内容必须有看点，不能是流水账**：提示词里硬性要求一条具体事件线——
  糟心事/小插曲、一句吐槽、一点反差或轻八卦，并且要具体到几点、多少钱、什么店
- 句子数跟着图数走（`4 + 图数`，夹在 5~9 句），保证每张图旁边都有话说
- **排版强制用 `photo` 主题**（见下），不看账号的长文主题设置
- 校验阈值放宽（`min_words=20`），否则长文那套 500 字下限会一直报警告
- 每张图 45~60 秒，所以 3 张图约 2~3 分钟，全程有阶段提示

#### `photo` 排版主题（看图日常）

长文那几套主题里，图片只是"插花"，`img` 样式是 `margin:0 auto`——**没有上下留白**，
套在晒图稿上就变成"文字贴图、图贴文字"，看着闷；而且长文的 `strong` 带黄色高亮底，
在晒图稿里只会显得脏。

所以单独加了 `render.THEMES["photo"]`：

- `img`：`margin:8px auto 12px` + `border-radius:14px` + 轻投影，图才"立"得起来
- `p`：`margin:0 0 24px`，正文行高 2.05，读起来松
- `strong`：纯黑加粗，**去掉黄色高亮**
- `caption`：居中浅灰，和图之间留 26px

`pipeline.account_theme()` 里：`content_mode == "photo"` 的号**强制返回 `photo`**，
因为这两套排版是给两种完全不同的内容形态准备的，混用一定难看。

另外图片在正文里的位置也调整过：原来最后一句话后面挂一张图会显得"没写完"，
`_photo_post_markdown()` 会把末尾孤零零的图往前挪到最后一个句子之前。

#### 单张配图「AI 重生成」

编辑器配图卡片上有 **AI 重生成** 按钮：点开填「补充要求」（可留空），
就把这一张用 AI 重新出一张**就地替换**，其余图和正文不动。

`pipeline.regen_ai_image()` 的要点：

- **场景描述优先取这张图上下文那句话**（看图说话的稿子里，旁边那句文案就是画面内容），
  没有再退回文章标题；调用方也可以直接传 `scene`
- 有绑定虚拟人物 → 走 `aigen.generate_scene`（人物参考 + 机位轮换）；没有就走普通生图
- 替换的是**第一张图**时，封面跟着重做（封面默认取第一张压字）
- `images_meta` 同步新地址和真实宽高，图注保留原来的
- 旧图文件如果**没有别的稿件还在引用**就删掉，否则反复重生成会把磁盘撑爆
- 接口：`POST /api/article/{id}/images/regen_ai`，body `{url, extra, scene}`

#### 设置页怎么填

设置页「AI 生图」区自己填 API（文本模型和生图模型是两套，分开配）。支持三类后端：

| 类型 | 填法 |
|---|---|
| OpenAI 兼容 images | 智谱 `https://open.bigmodel.cn/api/paas/v4` + `cogview-3-flash`（有免费额度），也支持 OpenAI/SiliconFlow |
| 通义万相 | 阿里云百炼 base_url + `wanx-v1`，走异步任务轮询 |
| 本地 SD | Stable Diffusion WebUI 的 `/sdapi/v1/txt2img`，Key 可留空 |

- 编辑页有「**AI 配图**」和「**AI 封面**」两个按钮。
- 提示词按账号人设自动带画面风格（穿搭→街拍氛围不露脸，美妆→平铺柔和光，美食→暖色特写）。
- 默认走**无脸/氛围感**路线：规避真人脸审核，也更适合当文章配图。

## 十一、多平台：公众号 / 头条号 / 大众点评
**两个平台从数据层就分开**，不是在一条流程里 if-else 判断：

| 层 | 怎么分 |
|---|---|
| 账号 | `accounts.platform`（`wechat` / `toutiao` / `dianping`），默认号也按平台各一个 |
| 稿件 | `articles.platform`，创建时从所属账号带过来，列表筛选不用 join |
| 投递 | 公众号走接口（`draft/add`），头条号走浏览器（只存草稿），大众点评未接入 |
| 登录态 | 头条号每个账号一份 `data/toutiao_state_<账号id>.json`，互不串 |

界面上对应关系：

- **账号页**：按平台分区；公众号填 AppID/AppSecret，头条号只填名字然后「扫码登录」，
  大众点评标「未接入」。老版本的单账号登录态（`toutiao_state.json`）会在你建好
  第一个头条号账号后自动认领，不用重扫。
- **工作台首页**：顶部一排平台筛选（全部 / 公众号 / 头条号 / 大众点评），
  稿件列表每行带平台标签；生成时的账号下拉也标了平台。
- **编辑页**：按稿件所属平台显示对应动作 —— 公众号稿件有「存入草稿箱 / 正式发布」，
  头条号稿件只有「存到头条草稿」，大众点评稿件只提示未接入。**不会出现拿公众号按钮
  投头条号这种情况**（后端也会拒：`pipeline.WrongPlatform` → HTTP 400）。

### 头条号的人工地雷

头条号除了扫码登录，还有**两道平台侧的硬门槛**。程序识别到就抛
`ManualActionRequired`，前端把原因顶在卡片上，不会只报一句"大概改版了"：

1. **要绑手机号** —— 页面整页变成「手机绑定」表单。
2. **要实名认证** —— 绑了手机还不够，头条要求实名（身份证 + 人脸）才能发文/存草稿。
   没实名时保存接口只会返回 `{"code":7050,"message":"保存失败"}`，一个完全看不出原因的错误码。

投递前会先调 `jingxuan_account_check` 查资质（`bind_mobile` / `real_name` / `finish`），
**不合格就直接拦住**，不会让你白填一遍内容再失败。这两步都只能人工去头条后台做。

### 头条没有「存草稿」按钮

和公众号完全不同：头条发文页底部只有 `预览 / 定时发布 / 预览并发布`，**没有存草稿按钮**。
草稿是前端自动保存的：内容一变，页面自己发一次
`POST /mp/agw/article/publish?...&save=0`。

所以投递流程是：

```
填标题 → 点正文激活工具栏 → 批量上传图片拿 CDN 地址
       → 一次性粘贴整篇正文 → 等页面自动保存 → 查草稿箱确认
```

**判断成功以草稿箱列表为准**（`draft_list` 里出现新的 `gid`），不要只看接口返回值。

⚠️ **绝对不要自己构造或重发这个保存请求**。曾经试过"抄参数、把 `save` 改成 1 重发"，
`save=1` 实际是**发布**——直接导致 2 篇测试文章真被发出去了，只能手动删。
现在代码只做观察者：等页面自己保存，失败就明确报错，绝不代替页面做写操作。

`save` 参数实测语义：`0` = 存草稿（正确用法）、`1` = 提交/发布（危险）、`2` = 发布失败 5009。

⚠️ 另一条踩坑提醒：**千万别在头条编辑器里按 Escape**。ESC 会让页面进入「放弃编辑」状态，
之后它发出的自动保存请求里 `content` 是空的，草稿箱里就留下一篇「只有标题、正文空白」的稿子。
`_dismiss_dialogs()` 的 `escape` 参数默认就是 `False`，只有还没开始写字的阶段才传 `True`。
（这个 bug 排查了很久：保存接口返回 `code:0` 看起来成功，但草稿字数一直是 0。）

### 判断"存成功"必须三看，少一个都会误判

1. **草稿箱新增了草稿**（唯一 id 字段是 `gid`，不是 `pgc_id`）
2. **那篇草稿的字数 > 0**（`graphic_extra.content_word_cnt`）——标题一填完页面就会先自动存
   一篇空壳草稿，只看"新增"会把它当成功
3. **保存请求里真的带了正文**（`content` 字段长度够）——同理，那次空壳保存也返回 `code:0`

`_verify_saved(min_words=...)` 和 `_save_draft_via_api(min_content=...)` 就是干这个的。
另外 `_fill_body()` 会在粘贴后核对编辑器实际字数，填不进去就重试，三次都失败就**中止**，
绝不留空稿。

### 头条正文图片必须走它自己的图床

正文里写本地路径或别家 URL，头条编辑器都不认。正确做法：

1. **先点正文编辑器**——填完标题后焦点在标题框，正文工具栏整体失活（按钮带 `disable` 类），
   这时点「图片」按钮**毫无反应**。这是"打不开上传面板"的真因，必须先点一下正文。
2. 点「图片」→ 打开的是 **`byte-drawer` 抽屉**（上传图片/免费正版图片/热点图库/我的素材），
   **不是系统文件选择框**——用 `expect_file_chooser` 等必然 15 秒超时（踩过）。
3. 抽屉里有 `input[type=file]`，直接 `set_input_files` 就能上传。
4. 监听 `POST /spice/image` 的响应，里面有 `data.image_url`（头条 CDN 地址）。
5. 把 CDN 地址拼成 `<p><img src="..."></p>` 粘贴进编辑器，头条会自动包装成 `pgc-img` 结构。

`_upload_images()` 做的是：开一次抽屉，批量传完所有图拿到 `{本地路径: CDN地址}`，
关抽屉，然后正文那边直接用 CDN 地址——每张图只传一次，也不去点抽屉里那张图试图"插入"。

### 7050「保存失败」的真正原因：`sec-ch-ua` 暴露了 HeadlessChrome

这是整个项目踩得最久、最隐蔽的一个坑，记录完整结论，别再重复排查。

**现象**：头条发文页填好标题+正文后，页面自己的自动保存接口
`POST /mp/agw/article/publish?save=0` 一直返回
`{"code":7050,"message":"保存失败"}`，但**同一个人在自己浏览器里操作就能存**。

**排查过程中被逐一排除的因素**（都不是原因，别再往这些方向查）：
- 实名认证（接口返回 `verified.finish=true`、`real_name` 有值）
- 封面/必填项（`展示封面`、`投放广告` 都选上也照样 7050）
- 内容长度/完整性（772 字和 130 字都失败）
- 空 key：`save=1` 是**发布**不是存草稿（曾因此误发文章，绝对别用）、`save=2` 返回 5009
- 无头模式（`headless=False` + xvfb 一样失败）
- 剪贴板粘贴被识别（改成逐字 `keyboard.type` 一样失败）
- `storage_state` 缺 IndexedDB（改成持久化 profile 后仍然失败，但 profile 仍值得保留）
- 缺 `a_bogus` / `msToken` / `tt-anti-token` / `x-secsdk-csrf-token`（这些其实都有）

**真正的原因**：请求头里的客户端提示

```
sec-ch-ua: "HeadlessChrome";v="159", "Not/A)Brand";v="8", "Chromium";v="159"   ← 被拒
sec-ch-ua: "Google Chrome";v="159", "Not/A)Brand";v="8", "Chromium";v="159"    ← 通过
```

`sec-ch-ua` 是浏览器在**网络层**发的，`navigator.userAgent` 改了它也不变，
所以前面所有"改 UA"的办法都无效。唯一的办法是用 CDP 连 `userAgentMetadata` 一起覆盖：

```python
cdp = ctx.new_cdp_session(page)
cdp.send("Network.setUserAgentOverride", {
    "userAgent": CHROME_UA,                      # 普通 Chrome UA
    "acceptLanguage": "zh-CN,zh;q=0.9,en;q=0.8",
    "platform": "Win32",
    "userAgentMetadata": {                        # ← 关键，它决定 sec-ch-ua
        "brands": [{"brand": "Google Chrome", "version": "159"},
                   {"brand": "Not/A)Brand", "version": "8"},
                   {"brand": "Chromium", "version": "159"}],
        "fullVersion": "159.0.8154.6", "platform": "Windows",
        "platformVersion": "15.0.0", "architecture": "x86",
        "model": "", "mobile": False, "bitness": "64", "wow64": False,
    },
})
```

改完之后**同样的操作 2 秒内就返回 `{"code":0,...}` 保存成功**。
代码里是 `_apply_client_hints()`，在每个页面创建时自动调用。

> 怎么定位到的：让用户在他自己浏览器里复制一次「保存成功」的请求 cURL，
> 两边的表单字段（`save`、`title_id`、`draft_form_data`、`pgc_feed_covers`）逐项对比都一样，
> 差异只能落在请求头上，于是逐个头比对，撞出 `sec-ch-ua`。

**另一个容易误判成"没存上"的坑**：草稿列表接口里草稿的唯一 id 字段叫 **`gid`**，
不是 `pgc_id` / `item_id`。`_draft_ids()` 早先漏了 `gid`，结果草稿明明存进去了，
校验却永远返回"草稿箱没新增"。判断成功**以草稿箱列表为准**，不要只看接口返回值。

**账号登录态用持久化 profile**（`data/tt_profiles/acc_<id>/`），不用 `storage_state`：
后者只有 cookies + localStorage，IndexedDB 会丢。profile 目录删掉就等于退出登录。

排查用 `python tools/toutiao_cli.py probe --account 3`（`--account` 传头条号账号 id），
它会报告 `account_ready` / `account_gate`（bind_phone 还是 verify）、选择器命中和草稿数。

## 十一、Docker 打包踩坑

打包时踩到的三个坑，都写进 Dockerfile 注释了，这里汇总一下：

**1. `playwright` 的 node 驱动缺 `libatomic.so.1`**

`python:3.12-slim` 里没有这个库，`python -m playwright install` 一启动就报：

```
/usr/local/lib/python3.12/site-packages/playwright/driver/node:
error while loading shared libraries: libatomic.so.1: cannot open shared object file
```

注意报错发生在**装浏览器之前**——是 playwright 自己跑不起来，不是浏览器缺依赖。
apt 里补一个 `libatomic1` 就行。

**2. 官方浏览器 CDN 在国内基本下不动**

`cdn.playwright.dev` 实测 **0 KB/s**（200MB 的 Chrome for Testing 卡在 0%），
换 `https://cdn.npmmirror.com/binaries/playwright` 之后 **19.5 MB/s**。
Dockerfile 里做成了 `PLAYWRIGHT_DOWNLOAD_HOST` 参数，默认走 npmmirror。

**3. 中文字体不打进去，封面全是方块**

封面是 Pillow 往图上压中文标题，slim 镜像没有中文字体。
装 `fonts-noto-cjk` + `fonts-wqy-zenhei` 即可（`cover.py` 的候选字体路径里都有）。

另外：`python:3.12-slim` 现在是 Debian trixie，`libpng16-16` 这类带 `t64` 改名的包
不要写死在 apt 里——Pillow 的 wheel 自带 libjpeg/zlib，用不着，写死反而会在新版基础镜像上构建失败。
